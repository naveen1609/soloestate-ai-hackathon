### 1. Shared delivery authorization bindings (HIGH defect — fixed)

Root cause: `authorize_delivery()` (`backend/app/caps.py`) granted the `in_thread` basis on observed status + caller-asserted `thread_fresh` + routine category alone, with no check that the destination, channel, lead or thread belonged to the identity; the `link` basis checked only status + verified destination, so an active link authorized sends for any lead once the destination matched. A rollback-only probe against the pre-fix code showed all six attacks authorizing: wrong destination, wrong channel, wrong lead, no thread evidence, 25h-stale link (`authorized=True`, basis `in_thread`), and an active link used for a different opted-in lead (`authorized=True`, basis `link`).

Fix: the evaluator now re-reads the link row by id and verifies every binding from persisted state — channel match, lead match, live status (revoked/superseded refuse), destination against `verified_destination` (link) or the channel-defined sender normalization (new `normalize_sender()` in `identity_links.py`: WhatsApp digits to +E.164, website handles opaque-exact), thread binding (claimed conversation exists, belongs to the link's lead, website handle pinned to the exact conversation), and the 24h window from the link's persisted `created_at` on the database clock (created_at predates any later inbound, so freshness is sound; staleness fails closed). The `thread_fresh` parameter is removed — no caller assertion can establish a basis. A conversation id supplied with link basis is cross-checked the same way (a stray isolated thread refuses with `thread_mismatch` instead of leaking canonical context). New precise refusal reasons: `thread_mismatch`, `thread_expired`. Suppression, contact, archived-lead, permission, category, policy, cap and cooldown gates are unchanged, as are the existing POL-01/POL-05 link-basis results.

Tests: `test_pol06_observed_in_thread_requires_full_bindings` (valid in-thread plus wrong destination/channel/lead/conversation×3/absent thread), `test_pol07_stale_revoked_and_cross_lead_links_cannot_authorize` (25h expiry, superseded, revoked, opted-in cross-lead decoy), `test_pol08_website_thread_and_gate_refusals_keep_valid_bindings` (website handle binding + divergence, suppression and opt-out refusing despite a valid `in_thread` basis, link-basis thread cross-check). ### 2. Booking lock ordering (inconsistency — fixed)

Investigation mapped every lock in the production call graph (`booking_requests` propose/confirm/decide/commit/cancel, `_booking_snapshot`, owner decide, owner prepare/commit/cancel/reject, tool request_approval/book_site_visit, slot/generate/deactivate, visits outcome, `guard_booking`/`guard_slot` triggers). All paths except one already follow the §6 total order `run → approval → resource → slot → property → lead` (the trigger re-locks approval → resource → slot → property → lead verbatim; `_booking_snapshot` documents and implements it; owner/tool paths compose it; replacement/cancel/deactivate/slot-creation take compatible prefixes).

Genuine defect, in `booking_requests.commit` only: it took lead/property `FOR SHARE` before the resource lock (inverted vs §6) and then upgraded property SHARE → UPDATE inside `_booking_snapshot`, a classic deadlock cycle against owner/tool paths holding resource locks while wanting the property lock (surfacing as retryable 503 on hit). Capacity integrity itself was never lost (controls-row serialization plus the snapshot's and trigger's under-UPDATE checks backstop it), but the order violation is fixed regardless.

Fix: `commit` now locks `controls → request → resource → slot → property(FOR UPDATE directly, never upgraded) → lead(SHARE)`, with the missing-slot INSERT deferred until after the problems evaluation so refusals write no slot rows. Every later re-lock (snapshot, trigger) is a no-op on held locks. Expiry/policy/integrity evaluation moved with the fresh clock (see 3). `propose`/`confirm`/`decide` keep advisory-only checks (no booking locks; commit revalidates authoritatively) — verified consistent, unchanged.

Correction to the correction, found by `test_apr04_past_window_expires_and_fresh_request_allowed` failing on the first reorder (commit on a windowless `awaiting_owner` row raised instead of expiring): the governing-window extraction now tolerates a missing window through the lock phase (resource/slot locks skipped) and the window check sits after the status gate, restoring the pre-fix exit order (expiry envelope / status raise before any window requirement) while keeping evaluation on the fresh post-lock clock.

Tests: `test_sch16_same_property_capacity_race_refuses_gracefully` (capacity-1, two resources, barrier-aligned: exactly one booking plus a graceful `site_capacity` envelope), `test_sch17_mixed_owner_autonomy_race_single_winner` (owner vs autonomy on one slot: exactly one booking, loser graceful per path, never 503), `test_sch18_deactivation_race_preserves_booking_or_refusal` (deactivate vs commit XOR with exact forms). All use independent connections with barrier alignment and bounded 503 retries per the documented contention contract; retries realign, so deadlock-freedom rests on the total-order proof above with these tests pinning positive outcomes. PENDING: final suite result.

### 3. Notice/expiry recheck on a fresh clock (defect — fixed)

### Root cause and evidence design

The corrections-session freshness check used `identity_links.created_at`: identity lifecycle metadata, not proof of inbound. It authorized fresh identities with no inbound at all and expired active conversations 24h after identity creation. A rollback-only side-by-side probe (previous evaluator reconstructed from the recorded diff vs the new one, same fixtures) showed the old code wrong on all three discriminating scenarios — fresh identity without inbound authorized, 48h identity with fresh inbound refused, fresh identity with 25h-old inbound authorized — while the new code is correct on all three.

The fix uses only existing persisted state, so no migration was added (`0012_channel_delivery.sql` stays reserved for D2; see the §16 plan note). `_latest_qualifying_inbound()` joins `conversation_messages` to `crm_operations` by request key: a message qualifies only as customer-role with a visitor (token-authenticated website ingress; the sole production writer is token-gated chat.send) or channel (provider-verified ingress; D2 webhooks will write these) operation actor. Owner-authored, system and outbound rows can neither open nor extend the window. Effective time is the provider event instant from the ingestion response envelope when present (a late webhook arrival cannot manufacture a fresh window), else the persisted receive instant; future-dated, unparseable, or receipt-incoherent timestamps are invalid and skipped. Freshness is strictly within 24h of one database-clock instant read per evaluation. All other gates (bindings, permission, suppression, archive, handoff, category, stop, cap, cooldown) are unchanged, as is link-basis behavior.

D1 tests use a server-only harness (`_record_inbound` in test_d1_database.py) writing the same rows real ingress produces, under the conversation lock with gapless seq. No production endpoint, flag, or client input can assert authentication.
