## Test boundaries and limitations

The five dedicated-empty-database schema cases still need a separate TEST_DATABASE_URL; skips are not passes. The browser live-Meta case stays opt-in. Citation validation is structural (retrieval membership, version existence, active status, exact quote match), not semantic certification; anything unverifiable persists as unsupported by design. Retrieval is deterministic keyword/scope ranking over active FAQs with no vector store. Simulation is owner-driven and internal; it never contacts, delivers, or infers contact permission. See [limitations](limitations.md).

## Grounding correction — 29 October 2026

An independent review confirmed the grounded path persisted model prose after only structural citation checks: a contradictory answer with a valid citation ID/version/quote was stored and displayed as grounded. The minimal correction assembles grounded bodies server-side from validated quotes under a fixed template (`Verified answer from the knowledge base:` plus `[FAQ <id> v<n>] <quote>` lines); model prose is never persisted in grounded or unsupported messages, and oversized assemblies persist as unsupported (`invalid_response`). No schema, endpoint, response-shape, registry or migration change was required.

Actual guarantee: every persisted assistant body consists solely of server-owned text — verified FAQ source excerpts for grounded answers, fixed text otherwise. Model confidence plays no role in grounding decisions and is displayed only as model-reported metadata. Residual limitation: topical relevance of the selected quotes follows deterministic retrieval ranking; the system does not semantically prove relevance, and selective quotation can omit context.

Frontend suite: **120 passed** with lint/typecheck clean (an initial 119/1 run under parallel load passed fully on rerun without code changes). Full backend regression was not rerun: the change is localized to grounded-body assembly plus one UI label, and all focused suites covering it are green.

## Stale-citation correction — 29 October 2026

A follow-up review found commit-time validation accepted a citation that was current at retrieval but superseded before commit: if FAQ v2 was published during inference, the draft still persisted as grounded on v1. The correction revalidates each citation inside the draft-commit transaction: cited `faqs` rows are locked with `SELECT ... FOR SHARE`, and a citation is rejected unless its version still equals the locked row's `current_version` with active status, alongside the existing retrieval-membership, version-existence, authorization and exact-quote checks. The shared lock serializes the commit against concurrent `FOR UPDATE` version/archive writes. A source revised or archived during inference persists the fixed unsupported text and moves the conversation to pending owner; historical messages and pinned citations are untouched, and superseded indicators remain read-time. No migration, registry, endpoint-shape or delivery change; server-assembled grounded bodies and informational-only confidence are preserved.

Focused B3 suites after the correction: **89 passed, exit code 0** in two runs — `tests/test_conversation_database.py` **28 passed, 1 warning in 320.47s** and `tests/test_faq.py tests/test_conversation.py tests/test_faq_database.py` **61 passed, 1 warning in 44.91s**, both with `--run-integrity-db-tests` (the warning is the existing Starlette/AnyIO deprecation in both runs). Four new tests cover superseded-version rejection, revision during inference, archival during inference, and a concurrent publisher serialized against the commit; unchanged valid sources, contradiction stripping, replay and pending-owner/handoff restrictions remain asserted by the retained suite. The first corrected run failed only in test cleanup (3 failed / 86 passed): committed fixtures were deleted inside the fixture transaction while commit locks were held (`LockNotAvailable`). The fix defers committed-fixture deletion to fixture teardown after rollback; the orphaned fixtures from that run (3 FAQs, 5 versions, 6 operations, identified by exact IDs) were deleted with probe-confirmed zero remaining, and a post-run probe confirmed zero leftover fixtures. No assertions were weakened. Full backend regression was not rerun: the change is localized to commit-time validation plus tests.

## Enforcement-boundary corrections — 29 October 2026

Read this report's B3 history wording with the enforcement layer made explicit; the behavior is unchanged, only the attribution is corrected.

- Append-only history is **API-enforced, not database-trigger-enforced**. No update/delete API routes exist for FAQ versions or conversation messages, and BFF allowlist tests pin their absence. Migration 0007 provides shape constraints (CHECKs, foreign keys, grounded/unsupported consistency) and RLS enablement, but deliberately no forbid triggers — they would break exact fixture cleanup ([decisions](DECISIONS.md)). So "immutable history" and "append-only messages" above mean the API offers no mutation path; a privileged database role is not trigger-blocked from rewriting rows.
- Owner authorization is **single-owner API-enforced, not multi-tenant database isolation**. There are no tenant IDs and no per-tenant boundary at any layer; the BFF session plus `require_owner` admit the single owner. RLS is enabled on all 18 tables including the four B3 tables with PUBLIC revoked (confirmed by the review's read-only checks), as defense-in-depth; the trusted local app role bypasses RLS, so owner-only access holds at the API/session layer. Do not read "private RLS" as multi-tenant isolation. [Limitations](limitations.md) already states single-owner without multi-tenant identities.
- Fixture scope: `test_faq_database.py` still rolls every write back, so its header stands. `test_conversation_database.py` rolls back all writes except the three race-test FAQs (and their revision keys) committed on a separate connection and deleted by exact FAQ ID plus exact request keys at fixture teardown; its module header now says so.
