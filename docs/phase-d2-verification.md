### Finding 1 — lead-scoped cooldown and open-attempt checks (fixed)

- Root cause: `dispatch.stage_in_txn()`, `_transition()` and `_restage()` passed `open_attempts=0, acked_in_window=0` (the transition counted acknowledged sends for the same outbox row only), so separate logical messages to the same lead bypassed the contract-literal §11 rule. The D2 implementation had narrowed counting per outbox row ([superseded decision](DECISIONS.md)).
- Correction: new `caps.lead_delivery_counts()` derives both counts from persisted attempts/outbox rows under the already-held lead `FOR UPDATE` lock — open attempts (`staged`/`submitting`/`unknown`) across all of the lead's rows plus acknowledged sends in the trailing 24 h (`COOLDOWN_HOURS_DEFAULT`, §15), acknowledged-without-submit-instant (owner-resolved-sent, late-receipt advance) falling back to the attempt creation instant. The transitioning/restaging row excludes itself (`exclude_outbox_id`); failed/blocked/superseded attempts never count, preserving bounded retries. Scope is per-lead across channels (only WhatsApp stages via the outbox in D2). Same rule at stage, restage and transition.
- Tests (`tests/test_d2_limits.py`): `lim01` (open staged blocks), `lim02` (unknown blocks), `lim03` (submitting blocks), `lim04` (recent ack blocks), `lim05` (two-row stage race, threads + barrier, committed with exact-ID cleanup + caps save/restore: one staged, one `cooldown_active`), `lim06` (other lead unaffected). All five failing tests failed on the old code first (second row staged / both raced rows staged); `lim06` guards throughout. Existing `dlv01` (self non-block) and the definitive-failure retry test prove the preserved halves on rerun.

### Finding 2 — reservation acquire/validate split (fixed)

- Root cause: `_transition()` reused the acquisition-style `used >= cap` headroom check on a unit the row already held, so the final permitted reservation was rejected at submission (`cap 25, used 25 → blocked`).
- Correction: `caps.authorize_delivery()` gains a `reservation` mode — `None` keeps the acquisition headroom check (staging, restage-without-reservation, all D1 callers unchanged); a held `{'reserved', 'day'}` validates ownership instead (reserved flag, recorded day, ledger-row presence) and fails closed with `reservation_invalid` otherwise, so no unreserved submission slips through. `_transition()` and `_restage()` (when the row holds a reservation) use validation mode. Held units stay valid across midnight and cap changes on their recorded day; refunds still fire exactly once on blocked/failed/abandon paths and unknowns still hold. Per-row unit proof would need reservation rows (schema change, not authorized) and was not invented.
- Tests: `lim10` (cap 1: first submits, second cannot reserve — guard, passes throughout), `lim11` (cap 25: reservation 25 submits — failed old with `blocked`), `lim12` (two-lead race for the final unit, committed: one stages, one `cap_exhausted`, winner drives to `sent` — failed old at the drive), `lim13` (transition/replay never double-charges — guard), `lim14` (restage under a full cap skips `cap_exhausted` without bypass — guard), `lim15` (requeue under a full cap raises — guard). Existing stop-block (refund-once) and unknown-hold tests prove the preserved accounting on rerun.

## Receipt/owner/sweeper lock-order unification — 4 November 2026

Independent review found an attempt↔outbox lock-order inversion: receipt reconciliation and acknowledgement selected the attempt by provider ID and locked it before the outbox, while the sweeper and owner-resolution paths locked the outbox before the attempt, so two contenders could deadlock. - Chosen protocol (`dispatch.LOCK_PROTOCOL`, every dispatch path audited: stage, transition, acknowledgement, definitive failure, unknown landing, receipt apply/drain, sweeper, owner resolution, resend, requeue): `webhook_events` row (receipt path only) → per-provider-ID receipt advisory lock → `delivery_outbox` → its `delivery_attempts` → identity link → lead → automation controls → business policy → immediate-reply policy → delivery caps as a leaf. Owner immediate-reply policy updates lock only the policy row and wait on nothing else, so they cannot close a cycle with dispatch paths that take the policy last.
- Lookup-before-lock: provider-ID attempt lookups are unlocked peeks (`_receipt_attempt_peek`) that never authorize a write; receipt paths re-derive ownership under the outbox→attempt locks (`_lock_receipt_rows`) and stale peeks degrade to the existing monotonic/stale guards (superseded, owner-resolved, ID mismatch), never to writes on the wrong rows.
